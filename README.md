# 订单监听 · Portfolio Watch

监听 Binance 合约公开带单对象的交易操作、带单余额和资金划转，提供中文管理页面、Telegram / Bark 通知。支持配置 U 本位合约 API 账号并按带单员的新成交自动提交市价跟单。跟单默认关闭，需要在账号关联中单独开启。

## 功能

- 根据昵称搜索公开带单对象，添加监听；每个对象可独立开启、暂停。
- 带单员和跟单账户支持拖动卡片排序；方向键可跨页移动，顺序保存在服务端。
- 交易记录展示：交易对、多空操作、成交数量、均价、成交金额、已实现盈亏、成交时间。
- 区分开多、平多、开空、平空。单条记录不能可靠区分全平与部分减仓。
- 展示当前带单余额及资金转入 / 转出历史；只对实际资金划转发送通知。
- 全局可调轮询频率（10～86400 秒，默认 60 秒）、每页数量（1～20 条，默认 20 条）。
- SQLite 持久化数据、同步位置、通知队列；重启去重、故障退避、两种通知渠道独立重试。
- 单容器部署，无第三方 Python 依赖；GitHub Actions 测试并发布 amd64 / arm64 镜像到 GHCR。

## Docker 部署

```sh
git clone https://github.com/zhshengjun/order-monitor.git
cd order-monitor
cp .env.example .env
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

把生成的随机口令填入 `.env` 的 `ADMIN_TOKEN`，然后：

```sh
docker compose up -d --build
```

访问 <http://localhost:8080>，使用 `ADMIN_TOKEN` 登录。搜索“熬鹰”，选择“熬鹰资本”添加。组合 ID 为 `5075281354358777856`。

默认端口仅绑定服务器回环地址。远程访问可以通过 SSH 转发：

```sh
ssh -L 8080:127.0.0.1:8080 user@your-server
```

若需要公开访问，使用 HTTPS 反向代理并设置 `COOKIE_SECURE=1`。不要把访问口令或通知密钥提交到 Git。SQLite 数据卷含通知凭证，需要保护访问权限。

## 本地运行

Python 3.9+ 可运行，Docker / CI 使用 Python 3.13。

```sh
export ADMIN_TOKEN='请替换为至少16位的随机口令'
python3 app.py
```

默认 `127.0.0.1:8080`，数据库在 `data/monitor.db`。通知在前端“通知与设置”配置，未启用任何渠道时仅在页面记录。

### Telegram

在 Telegram 的 BotFather 创建机器人，把 Bot Token 和 Chat ID 填到设置页。先与机器人发起对话，或把机器人加入目标群并允许发消息。启用开关并保存。Token 保存后不回显，输入框留空保留原值。

### Bark

填写 Bark 服务根地址（默认 `https://api.day.app`）和 App 中的 Device Key，启用并保存。使用服务端 `/push` JSON 接口，可接入自建 HTTPS Bark 服务。 测试和实际发送失败时，页面与服务日志显示脱敏错误类型或 HTTP 状态码；成功表示服务端已接受请求，不能单独证明手机已展示。

## 网络配置

默认读取 `https://www.binance.com`，不带 App 登录令牌。以下是启动环境变量，不通过页面修改：

| 变量 | 默认值 | 作用 |
|---|---|---|
| `ADMIN_TOKEN` | 必填 | 管理页面访问口令，至少 16 位 |
| `BINANCE_BASE_URL` | `https://www.binance.com` | 上游 HTTPS 入口 |
| `HTTPS_PROXY` / `HTTP_PROXY` | 空 | 可选 HTTP CONNECT 代理，供 Binance 和通知请求使用 |
| `DATABASE_PATH` | 本地 `data/monitor.db` | SQLite 文件路径 |
| `HOST` / `PORT` | `127.0.0.1` / `8080` | 本地监听；容器内部为 `0.0.0.0:8080` |
| `COOKIE_SECURE` | `0` | HTTPS 部署设置为 `1` |

容器中的 `127.0.0.1` 是容器本身。代理地址需要能从容器访问，例如 Docker Desktop 上的 `http://host.docker.internal:7890`（端口以实际配置为准）。只支持 Python 标准库 HTTP 代理，不直接支持 SOCKS。程序不会修改系统代理或关闭证书校验。

## 同步与通知语义

1. 首次轮询读取最近一页作为历史基线；添加监听之后发生的交易即使在首次同步完成前才出现，也会作为新交易处理。历史回填由独立任务进行。
2. 后续轮询默认每页 20 条，逐页回溯到已保存的时间边界并额外读取一页，最多 50 页；超过范围显示错误并保留同步位置，不静默跳过缺口。
3. 暂停对象会取消其未发送通知；恢复会补查暂停期间新增记录。首次同步失败后，添加监听之前的旧订单仍不会通知。订单先保存并进入通知队列，再查询资金划转；划转接口慢或失败不会丢弃新订单。
4. 交易接口没有提供订单 ID；同一轮询中，同币对、买卖方向、多空方向和毫秒时间相同的成交先合并数量并计算加权均价，再创建一个跟单任务。原始成交按数量、均价和盈亏等字段去重保存，用于历史重放。如果同一订单的更多明细在后续轮询才出现，系统按累计成交量的差额补一笔增量跟单任务，增量均价由两次累计成本之差换算，虚拟仓位同步累加，不会因此停止跟单；只有累计成交量回退（数据异常）才暂停相关跟单并提示核对。缺少唯一成交编号时仍无法保证逐单精确性。
5. 余额仅显示当前快照，不产生差异事件或通知；资金转入和转出记录会单独通知。
6. 每个事件与通知任务在同一数据库事务提交。渠道失败独立退避重试；已成功渠道不会因另一个失败而重发。外部服务“已接收但响应丢失”仍可能导致重试重复通知，不能承诺 exactly-once。
7. 仅给事件产生时已启用的渠道创建通知，不在启用渠道时追发历史。关闭渠道后待发送任务会取消。
8. 监听对象有限并发采集，跟单与通知使用独立工作线程。频率是最短轮询间隔，网络超时或对象较多时实际周期会更长。
9. 这些是 Binance 客户端使用的非正式公开接口，字段、访问限制、数据延迟可能变化。程序无法保证实时性，也无法看到未公开持仓或撤单。

## API 对应关系

公共路径前缀 `/bapi/futures/v1/friendly/future/copy-trade/`：

| 功能 | 方法 | 路径 |
|---|---|---|
| 搜索 | POST | `home-page/query-list` |
| 详情 / 带单余额 | GET | `lead-portfolio/detail?portfolioId=...` |
| 操作记录 | POST | `lead-portfolio/order-history` |
| 转入转出历史 | POST | `lead-portfolio/transfer-history` |

前端使用本服务的 `/api/*` 接口，管理 API 均需登录；`/healthz` 仅提供进程健康探针。页面每 5 秒刷新本地状态；选中账户的持仓约每 5 秒经服务端查询一次，其余当前页账户约每 60 秒查询一次。页面显示的盈亏比例为未实现盈亏除以当前持仓初始保证金，不含手续费和资金费；缺少有效保证金时显示“—”。带单员记录每页 10 条。页面金额展示为四位小数，价格最多四位小数并省略尾部零，实际交易计算使用原始精度。

## 数据与备份

首次启动会自动建库建表，首次同步只取最近 20 条作为基线，之后按已保存记录增量拉取。无需提前导入数据或 SQL。

数据位于 Docker 命名卷 `monitor-data`。容器入口会修正 `/data` 目录及 SQLite 文件的所有者，然后降权为 UID/GID `10001` 运行服务；也支持 `./data:/data` 绑定挂载。若自行覆盖容器 `user`、使用只读挂载或不允许 chown 的网络文件系统，需要预先保证目录及文件对 `10001` 可写。不要删除数据卷来解决升级问题，否则会丢失增量同步位置。

停止容器后备份整个卷，或使用 SQLite 在线备份 API；不要在写入过程中只复制主 `.db` 文件而忽略 WAL。当前没有自动清理历史，部署时注意磁盘空间。只运行一个应用实例，不共享数据库给多个副本。

### 排查搜索或同步失败

使用 `docker compose logs --tail=100 order-monitor` 查看脱敏日志。日志区分 DNS、TLS、超时、HTTP 状态和 JSON 格式错误；不记录代理地址、凭证、请求头或响应正文。`docker compose logs -f order-monitor` 可实时查看。容器内代理地址应使用容器可访问的地址，不能直接使用宿主机的 `127.0.0.1`。

跟单排查可搜索 `copy switch`、`copy decision`、`copy task` 和 `copy result`。其中 `disabled` 表示关联的自动跟单开关未开启，`before_start` 表示成交时间早于启用时间，`queued` 表示已创建跟单任务；预检查或下单失败会记录原因。日志不记录 API 密钥。

## 自动跟单

在“带单员与账户”页面保存合约 API 账号、关联带单员并点击“开启跟单”，无需等待首次历史同步；只处理本次开启后的新成交。重新开启会保留已有的跟单持仓和虚拟持仓。关闭跟单会取消未执行任务；已发送但结果未知的订单仍会查询状态。

开仓按带单员订单名义价值与其余额比例，乘以本账号合约账户的 USDT 钱包余额，按实时合约市价单步长向下取整；数量不足时按最小有效订单向上补足（同时满足最小数量和标记价格对应的最小名义金额）。开仓保证金按 10 倍杠杆校验，如果账户实际杠杆低于 10 倍则按实际杠杆计算，资金不足则跳过；程序不修改账户杠杆。最低订单可能大于比例计算结果。平仓先查询实际对应持仓，并按虚拟仓位比例缩减本关联已成交的跟单仓位；数量不足时仅在最小有效数量不超过实际持仓和本关联持仓时补足。跟单采用市价单，发送前检查买一／卖一相对带单均价的偏差不超过 3%；**这不是实际成交价格的保证**，市价成交可能产生更大滑点。

每次提交之前记录该次查询的 USDT 钱包余额、可用余额、带单余额、参考价和计划数量，同时保存客户端订单号；提交结果未知时只查询原订单，不再次提交。若查询持续失败，账号后续订单会等待，页面显示“待确认”，请核对 Binance 订单状态。每个账号与带单员的任务结果显示在账号卡片，跳过和成交会发往已启用的通知渠道。

下单前查询遇到网络、限流、HTTP 451 或服务器错误时，最多重试 3 次，间隔依次为 5、10、20 秒；每次重新执行资金、持仓、规则和价格检查。保证金不足等业务条件不自动重试。同一账户的后续任务等待前面的重试任务，避免交易顺序颠倒。下单请求已经发出而结果未知时，查不到持仓或委托也不能证明订单从未成交，系统只按原客户端订单号继续核对，不会自动重复提交。

开仓任务在首次执行或重试时，如果带单员开仓成交时间已超过 3 分钟，则跳过并通知；重试前如果已同步到该带单员同一交易对、同一方向的后续平仓或减仓，也会跳过并通知。带单员记录可能延迟，因此没有查到后续平仓不能作为原订单未成交的证明。

若通知提示 HTTP 451，可在“通知与设置 → 合约网络”测试服务容器对 `/fapi/v1/ping` 的访问和是否使用代理。该探针只验证公开网络接口，不能证明账号或下单接口权限。失败通知与服务日志会显示具体接口；对于下单提交结果未知，系统只查询原订单，不会重复提交。

持仓和账户接口使用官方 `fapi.binance.com`，容器网络需要能够访问该域名。API 密钥保存在 SQLite 数据卷中，不会在页面回显。程序只支持 HMAC API Key、U 本位 USDT 钱包余额，读取每个交易对当前配置的杠杆，不自动修改杠杆；价格偏离或可用余额不足等条件不满足时会跳过并通知。市价单标记价格会变动，交易所仍可能拒绝不满足实时过滤条件的订单。


保证金风险提醒：后台约每 30 秒逐个检查合约账户，风险率为维持保证金除以保证金余额，USDT 全仓和逐仓分别达到 60% 时通过已启用的 Telegram / Bark 发送；降到阈值以下后再次达到才重新通知。多资产模式及非 USDT 全仓暂不计算，失败写入服务日志。检查与通知受接口延迟、网络和轮询周期影响。

风险检查失败时也会通过已启用的通知渠道提示，相同错误在恢复前只提示一次。交易规则在进程内缓存 5 分钟；下单前仍实时查询账户余额、持仓与报价。增量同步额外读取一页以发现延迟记录；同一币对和方向的记录如果晚于后续交易到达，会暂停该关联的跟单并提示核对，避免按错误顺序改变虚拟仓位。延迟超过重叠页范围的记录仍可能无法发现。

当本地记录的跟单持仓总量超过账户对应实际持仓时，系统会跳过平仓并提示核对。币安汇总持仓无法区分手动交易和不同带单员的仓位，即使数量相同也不能完全确认归属；手动调整持仓后应检查跟单记录。

若带单员平仓前的虚拟持仓不足，系统仍会查询账户同方向实际持仓；有持仓时按“带单平仓名义金额 ÷ 带单余额 × 账户钱包余额 ÷ 当前可成交价格”估算平仓数量，并按步长取整、不超过实际持仓。此时平仓比例是估算值，可能平掉账户中手动建立或其他带单员产生的同币对仓位；没有实际持仓则跳过。

带单员卡片的“持仓”展示根据保存的交易历史重放的估算数量和加权开仓均价。后台持续逐页回填，直到接口返回空列表，并每小时重新核对；“更新并重新计算”从第一页重新同步。历史与实时监控分开存储，回填不会触发历史订单的跟单或通知。上游历史可能存在时间范围限制或缺失，回放结果并非交易所实时持仓；同一毫秒操作顺序无法确定时显示未知；平仓数量超过重放持仓时按零持仓继续。持仓重放完成且平仓前数量可计算时，跟单平仓优先按带单员的减仓数量占平仓前数量的比例计算；否则使用原有虚拟持仓或资金比例估算。账户同方向持仓可能包含手动交易或其他带单员的仓位。

带单员历史按交易对、买卖方向、多空方向、成交时间和成交数量去重；交易对和方向忽略大小写及首尾空格，数字按数值比较。公开接口没有提供唯一成交编号，若不同成交的上述字段完全相同，将视作同一记录。规则升级前的历史保存在数据库 `leader_history_before_v3`、`leader_history_before_v4` 和 `leader_history_before_v5` 表中。

手动更新使用独立临时表从第一页重新拉取，直到空页才在一个事务内替换正式历史；同步中断或接口失败时保留旧数据，下一次从失败页继续。后台历史请求之间至少间隔 5 秒，失败后退避 60、120、240、480、900 秒；这不改变实时监听间隔。同步期间页面显示已拉取条数、当前页及错误重试时间。
