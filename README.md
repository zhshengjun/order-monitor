# 订单监听 · Portfolio Watch

监听 Binance 合约公开带单对象的交易操作、带单余额和资金划转，提供中文管理页面、Telegram / Bark 通知。支持配置 U 本位合约 API 账号并按带单员的新成交自动提交市价跟单。跟单默认关闭，需要在账号关联中单独开启。

## 功能

- 根据昵称搜索公开带单对象，添加监听；每个对象可独立开启、暂停。
- 带单员和跟单账户支持拖动卡片排序；方向键可跨页移动，顺序保存在服务端。
- 交易记录展示：交易对、多空操作、成交数量、均价、成交金额、已实现盈亏、成交时间。
- 区分开多、平多、开空、平空。单条记录不能可靠区分全平与部分减仓。
- 展示当前带单余额及资金转入 / 转出历史；只对实际资金划转发送通知。
- 全局可调轮询频率（10～86400 秒，默认 60 秒）、每页数量（1～20 条，默认 20 条）。
- SQLite 持久化数据、同步位置、通知队列；重启去重、故障退避、两种通知渠道独立重试。
- 单容器部署，使用固定版本 urllib3 实现连接复用；GitHub Actions 测试并发布 amd64 / arm64 镜像到 GHCR。

## Docker 部署

```sh
git clone https://github.com/zhshengjun/order-monitor.git
cd order-monitor
cp .env.example .env
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

把生成的随机口令填入 `.env` 的 `ADMIN_TOKEN`，然后：

```sh
docker compose up -d --build
```

访问 <http://localhost:8080>，使用 `ADMIN_TOKEN` 登录。搜索“熬鹰”，选择“熬鹰资本”添加。组合 ID 为 `5075281354358777856`。

```sh

```

若需要公开访问，使用 HTTPS 反向代理并设置 `COOKIE_SECURE=1`。不要把访问口令或通知密钥提交到 Git。SQLite 数据卷含通知凭证，需要保护访问权限。

```sh
export ADMIN_TOKEN='请替换为至少16位的随机口令'
```

## 同步与通知语义

1. 首次轮询读取最近一页作为历史基线；添加监听之后发生的交易即使在首次同步完成前才出现，也会作为新交易处理。历史回填由独立任务进行。
2. 后续实时订单轮询默认每页 20 条；检查每页最后一条成交，未保存时继续读取下一页，已保存或遇到空页时停止，最多读取 50 页。
3. 暂停对象会取消其未发送通知；恢复会补查暂停期间新增记录。首次同步失败后，添加监听之前的旧订单仍不会通知。订单先保存并进入通知队列，再查询资金划转；划转接口慢或失败不会丢弃新订单。
4. 上游缺少唯一成交 ID。按带单员、订单更新时间、交易对、买卖方向和多空方向分组；组内成交数量相同的记录去重，数量不同的合并，累计数量和成交金额并计算均价。此规则假设每条成交的更新时间和数量固定；如果上游把订单更新时间变化或累计快照作为独立记录返回，可能重复跟单。数量相同但实际不同的成交也可能被去重。
5. 余额仅显示当前快照，不产生差异事件或通知；资金转入和转出记录会单独通知。
6. 每个事件与通知任务在同一数据库事务提交。渠道失败独立退避重试；已成功渠道不会因另一个失败而重发。外部服务“已接收但响应丢失”仍可能导致重试重复通知，不能承诺 exactly-once。
7. 仅给事件产生时已启用的渠道创建通知，不在启用渠道时追发历史。关闭渠道后待发送任务会取消。
8. 带单员按顺序循环采集订单，跟单与通知使用独立工作线程；订单历史请求在上一次请求结束后至少间隔 2 秒（包含失败、翻页和历史同步）。资金划转每个带单员约每 60 秒查询一次。失败的带单员按退避时间重试，网络超时或带单员较多会增加整轮耗时。
9. 这些是 Binance 客户端使用的非正式公开接口，字段、访问限制、数据延迟可能变化。程序无法保证实时性，也无法看到未公开持仓或撤单。

## 风控与可观测性

- **账户健康检查**：保存/更换 API Key 时先调用 `/fapi/v2/account` 验证；要求有合约交易权限。运行中每 5 分钟复查，连续 3 次失败或鉴权失败会自动暂停该账户跟单。
- **持仓对账**：每 60 秒比较交易所实际持仓与本地 `copied_positions` 归属。本地归属超过实际持仓时记录差异、触发严重告警并自动暂停该账户跟单；恢复一致后告警自动解除。
- **断路器**：自动暂停会关闭相关 `copy_live`、停用虚拟 session、取消未执行任务；已提交但结果未知的订单仍继续对账。页面账户配置里可“解除暂停”，解除后不会自动重新开启跟单。
- **告警分级**：事件分为 `info`、`warning`、`critical`。Telegram / Bark 可分别配置最低推送级别；同一告警按 key 去重，critical 每 5 分钟、warning 每 15 分钟、info 每 60 分钟最多提醒一次，消息会带持续时间和累计次数。
- **通知合并**：同一下单标的、方向、`orderTime` 的多条分批成交或多次跟单结果，会合并为一条通知（金额与数量累加，均价按成交额加权），不再逐条刷屏。合并发生在发送前，被合并的通知不再单独推送。
- **数字格式**：通知中的均价、数量会去掉多余的尾随零（如 `1697.070000...` 显示为 `1697.07`），金额保留四位小数；数据库和下单计算仍使用原始精度。
- **指标**：`GET /metrics` 暴露 Prometheus 文本格式，包含监听对象数、跟单任务状态、待确认订单、通知积压、活动告警、断路器、账户健康和对账超配数量。该端点不需要登录，部署时请只在内网暴露或由反向代理限制访问。
- **人工接口**：`POST /api/risk-breaker {"scope":"account:1","action":"reset"}` 解除暂停；`POST /api/copy-position` 修正归属；`POST /api/resolve-copy-task {"id":1}` 核对未知订单。

## 从 Python 版迁移

可以直接让 Go 版打开旧数据库，启动时会自动做增量迁移：

- 表结构只新增表和列（`virtual_trust`、`copy_tasks.reconcile_attempts` 等），不删除旧数据；
- `leader_history` 按当前身份规则重建，`records` 中的订单会导入 `go_fill_baselines`，已见过的成交不会重复跟单；
- 旧 `copy_tasks` 中 `pending/submitted` 的任务会继续处理，`submitted` 仍按原订单号对账，不会重发；
- 旧绑定的虚拟仓位会标记为不可信；带单历史回填完成后，重新关闭再开启跟单即可重算；
- **迁移前请先处理完旧版本里的手动平仓**。Go 版不再运行手动平仓流程，未完成的 `manual_closes` 会显示在页面并继续占用预留数量/阻止更换密钥，只能人工处理。

迁移前建议停掉旧进程并备份整个数据库（含 `-wal`/`-shm`）。新表和列对回滚是增量的，但 `leader_history` 重建和基线导入不可逆，回滚前请用备份。

## 数据与备份

首次启动会自动建库建表，首次同步只取最近 5 条作为基线，之后按已保存记录增量拉取。无需提前导入数据或 SQL。

数据位于 Docker 命名卷 `monitor-data`。容器入口会修正 `/data` 目录及 SQLite 文件的所有者，然后降权为 UID/GID `10001` 运行服务；也支持 `./data:/data` 绑定挂载。若自行覆盖容器 `user`、使用只读挂载或不允许 chown 的网络文件系统，需要预先保证目录及文件对 `10001` 可写。不要删除数据卷来解决升级问题，否则会丢失增量同步位置。

停止容器后备份整个卷，或使用 SQLite 在线备份 API；不要在写入过程中只复制主 `.db` 文件而忽略 WAL。当前没有自动清理历史，部署时注意磁盘空间。只运行一个应用实例，不共享数据库给多个副本。

### 排查搜索或同步失败

应用日志保存在数据卷的 `/data/logs`，按 UTC 小时切分；每分钟清理一次整段已满 24 小时的日志，因此每条日志大约保留 24～25 小时。查看最近日志：`docker compose exec -T order-monitor sh -c 'cat /data/logs/monitor-*.log | tail -n 100'`。实时查看当前小时：`docker compose exec order-monitor sh -c 'tail -f /data/logs/monitor-$(date -u +%Y-%m-%d-%H).log'`（跨小时后需重新执行）。应用正常日志不再写入 `docker compose logs`；容器入口或进程启动失败仍可能输出到该处。日志区分 DNS、TLS、超时、HTTP 状态和 JSON 格式错误；不记录代理地址、凭证、请求头或响应正文。容器内代理地址应使用容器可访问的地址，不能直接使用宿主机的 `127.0.0.1`。

跟单排查可搜索 `copy switch`、`copy decision`、`copy task` 和 `copy result`。其中 `disabled` 表示关联的自动跟单开关未开启，`before_start` 表示成交时间早于启用时间，`queued` 表示已创建跟单任务；预检查或下单失败会记录原因。日志不记录 API 密钥。

### 各环节耗时

新实时订单的首次发现时间与发现延迟会持久化保存，带单员交易记录和账户跟单记录均显示“发现延迟”（秒，保留三位小数）。旧订单、历史回填和历史基线没有可验证的首次实时发现时间，统一显示 `-`，不会用后来的再次采集时间补算。重复采集和订单增量更新保留首次发现值。

INFO 级别的 `timing stage=...` 日志用于定位延迟，单位为毫秒。用 `task=<ID>` 关联跟单任务、合约请求和结果通知，用 `target=<ID>` 关联带单员采集；分页另带 `kind`、`page`。每次请求独立记录成功或失败，不输出密钥、签名、请求参数、通知正文或原始异常。

| stage | 含义 |
|---|---|
| `poll_schedule` | 已到采集时间后等待调度的时间；首次调度为 unknown |
| `leader_detail` / `order_collect` / `poll_apply` | 详情查询、订单采集、获取处理锁并写入数据库 |
| `history_lock_wait` / `history_rate_wait` | 历史接口锁等待、限速等待 |
| `history_page` / `leader_request` | 单页总耗时、单次公开接口请求耗时（含读响应和解析） |
| `order_discovered` | 首次发现新订单：`discovery_delay_ms = discovered_at_ms - source_order_time_ms`；发现时间取该页返回时，排除后续分页、处理与入队等待。`source_time_field` 为 `orderUpdateTime`；这些是上游字段，不承诺是逐笔成交时间；历史记录标记 historical，统计实时延迟应排除它们。重复采集不会重复记录；同一订单后续增量不视为首次发现。通过 order_key 与 copy_enqueued 关联任务。 |
| `copy_enqueued` | 任务 ID、源交易时间和 `source_to_enqueue_ms`；包含上游发布延迟与本地发现、处理时间，不能单独归因于轮询 |
| `copy_pickup` / `copy_dequeued` | 工作线程获取锁和读取任务耗时；任务年龄 `task_age_ms`，以及重试到期后的 `ready_lag_ms` |
| `copy_preflight` / `futures_request` | 预检查总耗时、各合约接口耗时；POST/GET 区分提交和查询订单 |
| `copy_submit` / `copy_confirm` | 提交调用、后续确认查询耗时（即使超时也会记录） |
| `copy_response` | 交易所状态、`exchange_update_ms`、源交易到响应和入队到响应的延迟 |
| `copy_finalize` / `copy_attempt` | 保存终态并生成通知耗时、该次处理耗时 |
| `notification_start` / `notification_send` | 通知事件年龄、发送耗时，附 event、task、channel、attempt |

`duration_ms` 使用单调时钟；年龄与跨系统时间差使用墙上时钟，受时钟偏差影响。`task_age_ms` 在首次处理时反映排队时间，后续处理包含已执行时间和重试等待；结合 state、retries 和逐次日志判断。`exchange_update_ms` 是交易所返回的订单更新时间，不保证是精确成交时间；未返回时为 unknown。通知 `event_age_ms` 对交易操作从源交易时间算，对跟单结果从结果事件生成时间算，不能统一当作通知排队耗时。发送成功仅表示通知服务接受请求。

嵌套阶段的耗时包含子阶段，不应直接相加。`outcome=ok` 表示该代码块正常返回；`copy_attempt` 可能正常处理了跳过或待重试，交易是否成功仍以 `copy result` / 数据库终态为准。部署新版本后才开始收集，旧记录无法补回。

### 疑似清仓与账户持仓核对

当本地跟单虚拟记录表明带单员可能已全部平掉某币对、方向时，系统在关联的跟单任务结束后，只读查询账户对应方向的实际持仓；如果仍非零，就向已启用的通知渠道提醒。若平仓信号超时被跳过，也会在可判断疑似清仓时触发核对。持仓可能来自手动交易或其他带单员，提醒不会自动下单。查询失败会提醒一次并每 30 秒重试；订单仍待执行或确认时最多等待 30 秒再查询并在提醒中注明当前状态，不会自动重发订单。核对任务持久化，可在服务重启后继续。

该判断依赖本地已记录的带单员虚拟仓位；历史缺失、信号没有被发现、虚拟仓位为零或上游数据不完整时，无法保证触发提醒。账户持仓是查询时的快照，不代表其全部归属于该带单员。

币安公开接口、合约账户查询及跟单请求共用 HTTPS 连接池；TLS 验证、HTTPS_PROXY / NO_PROXY 与超时仍生效，提交失败不会由连接池自动重发。通知渠道保持原有连接方式。连接复用不能消除上游发布延迟，实际收益以部署后日志实测为准。

## 自动跟单

在“带单员与账户”页面保存合约 API 账号、关联带单员并点击“开启跟单”，无需等待首次历史同步；只处理本次开启后的新成交。重新开启会保留已有的跟单持仓；带单历史回填完成时，会按带单当前仓位重算虚拟仓位，漏掉的开仓不补单。历史未完成时沿用旧虚拟仓位并提示核对。每个账户/带单员会记录虚拟仓位是否可信：历史未完成、同一毫秒存在相反操作、成交回退或乱序时标记为不可信；不可信时，带单减仓量超过本地记录不会自动按实际持仓全平，而是跳过并提示核对。关闭跟单会取消未执行任务；已发送但结果未知的订单仍会查询状态。

所有订单使用订单更新时间 `orderUpdateTime` 判断三分钟时效，`orderUpdateTime` 与交易对、方向用于订单身份去重，是否晚于开启跟单也按更新时间判断；更新时间缺失、早于订单时间、明显超前或过期时跳过并提醒，不会自动补做旧订单。该字段是上游订单更新时间，并非已验证的逐笔成交时间，修改或撤单也可能改变它；历史分页和无唯一成交编号仍可能遗漏或混淆更新。平仓按带单员本次平仓数量占其平仓前持仓的比例，计算本关联需要平掉的数量，并以账户实际对应方向持仓封顶；带单员平完时，本关联也按 100% 平仓。无论带单员使用限价单还是市价单，跟单均使用市价单。单向模式带 reduceOnly。本地带单仓位从启用跟单后跟踪，可能缺少启用前或未发现的成交，因此减为零不保证带单员实际账户已清仓。价格偏离、可用余额与交易所规则等检查仍生效。分批成交按已观测的增量处理；如果订单在开启跟单前已有成交，但首次发现时没有历史基线，上游累计数量无法拆分出开启前后的成交，存在多跟的风险。

开仓按带单员订单名义价值与其余额比例，乘以本账号 USDT 钱包余额及该账户与带单员关联的跟单倍数，再除以执行参考价格，按市价单步长向下取整。每个关联默认 1 倍，可配置 0.0001 至 100 倍；原有旧版倍数不会自动启用。倍数在任务创建时固定，修改仅影响之后的新任务，同一订单的累计增量沿用首次任务倍数；旧版待执行任务按 1 倍处理。程序不会自动修改交易所杠杆。按当前实际杠杆检查可用保证金；最小数量或名义金额不足时按交易所最小有效订单补足。平仓按带单员减仓比例和实际跟单持仓计算，使用市价单；平仓数量始终以本账户实际对应方向持仓为上限。若带单员减仓数量超过本地记录的平仓前仓位，按本地实际跟单持仓全平。发送前检查盘口相对带单均价偏差不超过 3%；市价成交可能产生更大滑点。

每次提交之前记录该次查询的 USDT 钱包余额、可用余额、带单余额、参考价和计划数量，同时保存客户端订单号；提交结果未知时只查询原订单，不再次提交。若查询持续失败，账号后续订单会等待，页面显示“待确认”，请核对 Binance 订单状态。每个账号与带单员的任务结果显示在账号卡片，跳过和成交会发往已启用的通知渠道。

下单前查询遇到网络、限流、HTTP 451 或服务器错误时，最多重试 3 次，间隔依次为 5、10、20 秒；每次重新执行资金、持仓、规则和价格检查。保证金不足等业务条件不自动重试。同一账户的后续任务等待前面的重试任务，避免交易顺序颠倒。下单请求已经发出而结果未知时，查不到持仓或委托也不能证明订单从未成交，系统只按原客户端订单号继续核对，不会自动重复提交。

开仓任务在首次执行或重试时，如果带单员开仓成交时间已超过 3 分钟，则跳过并通知；重试前如果已同步到该带单员同一交易对、同一方向的后续平仓或减仓，也会跳过并通知。带单员记录可能延迟，因此没有查到后续平仓不能作为原订单未成交的证明。

若通知提示 HTTP 451，可在“通知与设置 → 合约网络”测试服务容器对 `/fapi/v1/ping` 的访问和是否使用代理。该探针只验证公开网络接口，不能证明账号或下单接口权限。失败通知与服务日志会显示具体接口；对于下单提交结果未知，系统只查询原订单，不会重复提交。

持仓和账户接口使用官方 `fapi.binance.com`，容器网络需要能够访问该域名。API 密钥保存在 SQLite 数据卷中，不会在页面回显。程序只支持 HMAC API Key、U 本位 USDT 钱包余额，读取交易对实际杠杆，不自动修改杠杆；价格偏离或可用余额不足等条件不满足时会跳过并通知。市价单标记价格会变动，交易所仍可能拒绝不满足实时过滤条件的订单。


保证金风险提醒：后台约每 30 秒逐个检查合约账户，风险率为维持保证金除以保证金余额，USDT 全仓和逐仓分别达到 60% 时通过已启用的 Telegram / Bark 发送；降到阈值以下后再次达到才重新通知。多资产模式及非 USDT 全仓暂不计算，失败写入服务日志。检查与通知受接口延迟、网络和轮询周期影响。

风险检查失败时也会通过已启用的通知渠道提示，相同错误在恢复前只提示一次。交易规则在进程内缓存 5 分钟；下单前仍实时查询账户余额、持仓与报价。实时订单轮询以每页最后一条成交是否已保存决定是否继续翻页；同一币对和方向的记录如果晚于后续交易到达，会暂停该关联的跟单并提示核对，避免按错误顺序改变虚拟仓位。排在已保存记录之后的延迟记录可能无法被发现。

自动平仓以该带单员实际跟单成交形成的本地数量为上限，并按带单员减仓比例计算；其他带单员和未关联仓位不会作为该带单员的平仓数量。当本地跟单持仓合计超过账户对应实际持仓时，部分平仓跳过并通知核对。若能确定带单员已全平，先保留其他带单员的已记录数量，最多平掉剩余的实际持仓；确认成交后按实际可归属数量和成交数量调整该带单员记录。如无可归属数量，则不下单并清除该带单员记录、发送通知；该处理以用户可能已手动平仓为前提，不改变其他带单员记录。订单结果不明时通知，并只查询原订单，其他跟单继续；待确认平仓数量从对应带单员的可用跟单数量中预留，若数量不足则跳过并通知，已跳过任务不会自动补单。单向模式使用 reduceOnly，双向模式指定对应 positionSide。

若本地虚拟仓位不足，且已完成的带单历史能够重放出可靠的平仓前数量，系统使用重放数量计算比例；否则跳过并通知核对，不再按账户资金比例猜测。

### 人工核对与未闭环处理

- 跟单记录中 `submitted`（待确认）的订单会先按 15 秒、30 秒、60 秒、2 分钟、5 分钟退避查询；连续 8 次仍无法确认时会单独提醒人工核对。系统只查询原订单，绝不重发。
- 页面跟单记录的“核对结束”按钮会先向交易所查询该 `clientOrderId`：只有交易所明确返回订单不存在（`-2013`/`-2011`）时才结束任务并写审计；订单仍在进行中则拒绝操作。
- 全平信号如果只部分成交，系统会自动把剩余跟单仓位重新排队补平，最多 3 次；仍无法完成时保留通知要求人工核对。
- 手动在交易所改仓后，可调用 `POST /api/copy-position` 修正本地归属：`{"account_id":1,"target_id":"...","symbol":"BTCUSDT","position_side":"LONG","quantity":"0.5"}`。该关联存在待执行/待确认订单时拒绝修正，并记录审计事件。

历史回放和虚拟仓位可能缺失带单员启用前或未发现的成交，不能保证等于交易所真实持仓；账户同方向持仓可能包含手动交易或其他带单员产生的仓位。

带单员卡片的“持仓”展示根据保存的交易历史重放的估算数量和加权开仓均价。仅点击“更新并重新计算”后，从第一页逐页拉取，直到接口返回空列表；重启后不会自动重新拉取。历史与实时监控分开存储，回填不会触发历史订单的跟单或通知。实时监听仍会增量保存新成交。上游历史可能存在时间范围限制或缺失，回放结果并非交易所实时持仓；同一毫秒操作顺序无法确定时显示未知；平仓数量超过重放持仓时按零持仓继续。持仓重放完成且平仓前数量可计算时，跟单平仓优先按带单员的减仓数量占平仓前数量的比例计算；否则使用已有虚拟持仓计算；无法确定比例时跳过并通知。账户同方向持仓可能包含手动交易或其他带单员的仓位。

带单员历史按交易对、买卖方向、多空方向、成交时间、成交数量和成交金额去重；交易对和方向忽略大小写及首尾空格，数字按数值比较。公开接口没有提供唯一成交编号，若不同成交的上述字段完全相同，将视作同一记录。规则升级前的历史保存在数据库 `leader_history_before_v3`、`leader_history_before_v4` 和 `leader_history_before_v5` 表中。

手动更新使用独立临时表从第一页重新拉取，直到空页才在一个事务内替换正式历史；同步中断或接口失败时保留旧数据，下一次从失败页继续。后台历史请求之间至少间隔 5 秒，失败后退避 60、120、240、480、900 秒；这不改变实时监听间隔。同步期间页面显示已拉取条数、当前页及错误重试时间。
